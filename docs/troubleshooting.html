Troubleshooting

When something is wrong

Failure modes actually seen on this rig, how each one looks, and what fixed it. Start with avrig check: its health lines name the component and usually the fix.

Argus will not start

“Cameras busy” / another instance

A camera can be opened by one process at a time, and Argus holds an instance lock. Close any other capture tool, stop hands-free mode (sudo systemctl stop avrig-auto), and find a holder with:

fuser /dev/video0          # which process has the camera
pgrep -af avrig

Started from the desktop icon, the reason appears in a dialog. Never kill -9 a process that is streaming: skipping stream-off can wedge the sensor until a reboot. Stop it with SIGINT / SIGTERM.

Config error

Every key in ~/.config/avrig.yaml is validated and unknown keys are rejected; the message names the key and the allowed range.

Recording is blocked

Preflight blocks recording on any FAIL. The ISSUES list in the GUI and the health lines of avrig check name it:

MessageFix
hardware frame sync is OFFavrig sync on (the boot service normally does this; check journalctl -u avrig-boot -b)
found 5/6 cameras · a camera failed / stalledSee “A camera is missing” below
only N GB freeOffload and prune (avrig offload, avrig prune)
… at N °C (limit …)Improve cooling; check the fan mode
IMU silentCheck the USB cable; the port (/dev/ttyUSB0) and the user's dialout group

Cameras stream but are not simultaneous

Signature: nominal fps, zero drops, everything looks healthy — but SYNC says FREE-RUN and the spread is tens of milliseconds. frame_sync_mode reset to 0 at the last reboot or driver reload. There is no other symptom, which is why Argus measures the lock every second and preflight requires it. Fix: avrig sync on.

Cameras starve with sync on

Signature: ~1 fps in bursts of 3–4 frames separated by ~2.5 s stalls; the kernel log shows the sensor's ISP asking for a reset. The deserializer's trigger switch is on external and nothing is driving the trigger input. Move it back to internal, or wire a 30 Hz, 1.8 V trigger (through a level shifter — 3.3 V over-drives it).

A camera is missing

  • /dev/videoN numbering is not stable. Plugging in another V4L2 device (a USB webcam) renumbers the cameras, and a camera that fails to probe shifts the others. Argus identifies cameras by the sensor's I²C bus and address in the device name (isx031 9-0043 …), not by node number; avrig wizard verifies physical positions one lens at a time.
  • To re-enumerate cameras, reboot. Reloading the driver can lose one port in a race with the deserializer's reset. Never write to the driver's sysfs bind/unbind — it panics the kernel.
  • Two ports on the second deserializer are unpopulated on this rig; their probe failures at boot are expected.

No cameras after a system update

Signature: v4l2-ctl --list-devices shows only /dev/media0. Two causes, possibly together:

  1. The device tree was replaced. An L4T package update overwrites the stock DTB that the camera overlay was merged into, and resets the boot entry. The rig avoids this by merging the overlay into a separately named DTB that L4T does not own, and pointing the boot entry at it. Check: grep -E "DEFAULT|FDT|OVERLAYS" /boot/extlinux/extlinux.conf.
  2. The vendor's patched camera modules were replaced by stock builds, and the sensor driver fails with “Unknown symbol” (journalctl -k -b | grep "Unknown symbol"). Reinstall the vendor modules for the running kernel, then reboot.

The camera driver package is locked to both the L4T release and the kernel version; after either changes, install the matching package.

Every camera port fails at the serializer

Signature: every port on both deserializers fails on the first register write (I²C NACK, probe error −5), while the frame-sync MCU on the always-on bus still answers. That is a hardware fault — the board has power but its camera section does not. Check the deserializer board's power input and reseat the board cable and the coax. On this rig both deserializers failed this way over several days and the board was serviced.

Format errors

The sensor is 1920 wide, never 2048. V4L2 silently clamps an out-of-range request (asking for 2048 returns 1920 with success), while GStreamer refuses with not-negotiated. Argus checks the negotiated format of every camera.

“Signal lost — No input source was detected” from GStreamer is benign on this platform when frames are flowing: the plugin queries an input concept the Tegra driver does not implement. It matters only together with zero frames — the cold-sync failure.

GNSS will not fix

Do not assume “indoors”. Check the receiver's RF report (avrig gnss --rf-enable, then the RF chip or gnss_rf.csv): an antenna reported OK with a pinned-low AGC and a high jamming indicator means broadband interference. On this rig that was the USB 3 hub the receiver was plugged into — USB 3 SuperSpeed noise sits on the GPS L1 band. Moving the receiver off the USB 3 hub and the antenna to open sky fixed it. gpsd owns the serial port: use gpspipe -w, not the device, to look at it.

Clock is not GNSS

The CLOCK chip stays amber until chrony disciplines from the GNSS receiver, which needs a fix and the one-time GNSS clock setup (sudo bash setup/gnss-clock/install.sh). Inter-camera alignment does not depend on it — that rides the shared TSC — but absolute UTC does. When looking for a PPS source, read /sys/class/pps/*/name: /dev/pps0 on a stock system is the kernel's synthetic ktimer, and binding to it produces convincing and entirely fictitious synchronisation.

Lab jobs

  • “Recording in progress” — offline jobs refuse to start while recording and stop if one starts. Wait for the recording to end.
  • Models missing — run avrig models --fetch --build once (~750 MB, ~30 minutes of engine building).
  • No calibration — 3D labels, visual speed, landmarks, reconstruction and datasets with camera poses need a registered calibration; some accept --nominal-geometry for rough, clearly marked results.
  • No trajectory — 3D labels in the world frame, map landmarks and reconstruction need avrig trajectory first, which needs a drive with a GNSS fix.

Foxglove and the phone page

  • Foxglove: Open connection → ws://HOST:8765. By default the server binds to 127.0.0.1; for another machine set foxglove_bind: 0.0.0.0 and a token, and connect with ?token=.
  • Phone page: http://RIG:8088/ with ?token= when remote_token is set. Marker buttons need both remote_markers: true and a token.
