How it works

How we made the rig work

Six cameras that expose together, timestamps that tell the truth, sensors on one clock, and a recorder that keeps going when one part fails. This page explains each layer and why it is built the way it is. The problems met on the way are on Engineering notes.

Design goals

  • Capture time, not arrival time. Every frame carries the time the hardware finished capturing it, to ~15 µs, on the same clock as the IMU and GNSS.
  • Hardware sync, verified continuously. All six sensors expose on one trigger, and the lock is measured every second, not assumed.
  • Every fault attributable. A dropped frame, a stalled camera, a lost lock, a disk error: each is logged with the camera, the time and the cause. A session that is not trustworthy says so.
  • The recording never waits for anything else. Previews, quality checks, guards, the phone page and Foxglove all hang off leaky branches or run at low rate on other threads. Neural networks and decoding run only after the drive.
  • Failures stay local. One capture thread and one pipeline per camera: a fault in one camera never stops the other five.

Architecture

Capture pipeline

The Tegra video input stamps every frame at end-of-frame from the SoC's TSC counter. Those stamps are excellent: about 15 µs of jitter, and all six cameras share the counter. The problem is that the TSC counts from power-on while CLOCK_MONOTONIC starts at kernel start, so the stamps look ~20 s “in the future”. GStreamer's v4l2src sanity-checks them, logs “Timestamp does not correlate with any clock, ignoring driver timestamps”, and silently stamps each frame with its dequeue time instead — which jitters by milliseconds whenever the CPU is busy.

So Argus does not let GStreamer capture. Each camera has its own capture thread that:

  1. opens the device, negotiates 1920×1536 UYVY at 30 fps (and checks the negotiated format, because V4L2 silently clamps out-of-range requests);
  2. dequeues mmap buffers itself and keeps the driver timestamp and the sequence number of every frame;
  3. maps the TSC time to the host clock (below) and pushes the frame into a GStreamer appsrc with the true capture time as its PTS.

GStreamer then only encodes and previews:

capture (V4L2 mmap, TSC time, sequence) → appsrc → tee
   → nvvidconv (NVMM) → nvv4l2h265enc → h265parse → splitmuxsink (Matroska segments)
   → preview:     rate-limited nvvidconv → RGBA appsink          (leaky, 1 buffer)
   → quality:     160×128 grey at ~1 Hz → appsink                (leaky, 1 buffer)
   → mount guard: videorate ≤ 4 Hz → queue leaky → 640×512 grey (leaky, 1 buffer)
  • Encoding is NVENC H.265 at 20 Mbit/s per camera, a keyframe every second, no B-frames and no reordering. Segments are keyframe-aligned (default 300 s) so a session splits into files with no frame gaps.
  • frames.csv is written by a probe after the encoder, so every row is a frame that reached the muxer: row n is the n-th video frame of that camera across its segments, by construction. Matroska rounds timestamps to 1 ms, so frames.csv (driver time, TSC time, sequence) is the timing authority and the container's timestamps are used only to seek.
  • Side branches are leaky with a one-buffer appsink: if analysis falls behind, frames are dropped from the branch, never from the recording. The mount-guard branch is rate-limited before its queue, so the colour conversion runs only 4 times a second.
  • Drops are gaps in the driver's sequence numbers, so a lost frame is detected even if nothing downstream notices.

Hardware frame sync

The ISX031 supports a readout trigger: with frame_sync_mode=1 the sensor starts its readout on an edge of the deserializer's FSIN pulse instead of its own crystal. Two independent settings must both be right: SW2, a physical switch on the deserializer board that selects the on-board generator or an external input, and frame_sync_mode, a per-camera driver control that defaults to 0 and is lost at every reboot or driver reload. Argus uses the internal generator.

Proving the lock

Free-running, the cameras share a clock through the deserializer, so they do not drift, but each starts at an arbitrary phase: over six restarts the worst spread was 22.4, 24.1, 25.9, 27.5, 28.2 and 31.5 ms — always under one frame period, never the same twice. A tight spread could therefore happen by luck, so Argus judges the lock continuously from driver timestamps of every frame set:

Turning it on safely: the warm start

Sync was not a matter of setting one control. In order, the team found that:

  1. With SW2 on external and nothing on the input, the sensors starve: bursts of 3–4 frames separated by ~2.5 s stalls and “Error in ISP, Need to reset” in the kernel log. SW2 must be on internal unless a 30 Hz, 1.8 V trigger is wired.
  2. On the first deserializer board, the FSIN trigger missed edges: about 8 dropped frames per minute rig-wide, always two-frame jumps, clustered by deserializer. After the board was serviced, the same test gave 0 drops in 2 minutes.
  3. Enabling sync on cold sensors breaks the rig. A boot service that set frame_sync_mode=1 before anything had streamed left four of six cameras delivering zero frames, with a restart storm. The same boot with sync off recorded cleanly; the same setting applied after the cameras had streamed once worked. A one-camera smoke test does not reproduce it — only six cameras at once do.

So avrig sync on always does a warm start: if nothing is streaming, it streams all six free-running for ~2 s, stops them, sets frame_sync_mode=1 on each camera, reads it back (the driver can clamp silently), restarts the streams and verifies the lock. The boot service (avrig sync on --boot) first waits up to 120 s for all six cameras to enumerate, retries once if the lock fails, and otherwise leaves the rig free-running so that preflight blocks recording until an operator acts. Every attempt is written to the audit log.

The warm-start boot path is the result of these experiments. It has been run by hand on the repaired hardware many times; a full cold boot through the installed service still has to be confirmed on this rig — check journalctl -u avrig-boot -b after the first reboot.

Clock model

  • TSC → host. Measured on this rig, TSC − CLOCK_MONOTONIC_RAW is constant to ±5 µs over 50 s (one oscillator), while plain MONOTONIC is slewed by chrony (~13 ppm). So mono = tsc − offset + (MONOTONIC − MONOTONIC_RAW), with the second term read back-to-back at each dequeue. The per-boot offset is estimated as the maximum of tsc − dequeue_raw: a frame can never be dequeued before it ends, so the maximum approaches the true offset from below, to within the minimum interrupt-to-dequeue latency. All cameras share the TSC, so inter-camera alignment is exact.
  • IMU. The MTi's own sample clock (SampleTimeFine) is fitted to the host clock, so the IMU's USB latency does not become timestamp jitter.
  • GNSS and UTC. clock.csv pairs MONOTONIC, MONOTONIC_RAW and REALTIME every 2 s; utc_ns = mono_ns + (real_ns − mono_ns) interpolated. With a GNSS fix and the GNSS clock installed, chrony disciplines realtime from the receiver (via gpsd's SHM refclock), and the CLOCK chip shows it.
  • Time marks (optional). With the camera trigger wired through a level shifter to the receiver's EXTINT input, every trigger edge is time-stamped in GNSS time (UBX-TIM-TM2), and verify fits TSC → GNSS time per frame.

The mapping and its parameters are written to manifest.json → timebase and timing, and clock.csv keeps the raw values, so it can be redone offline.

IMU and GNSS

  • IMU: Xsens Xbus / MTData2 frames, checksum-verified; packet-counter gaps are counted as lost samples; the status word (self-test, filter valid, SyncIn marker) is recorded in imu.csv. The FTDI latency timer is set to 1 ms by a udev rule — with the factory 16 ms, host-timestamp residuals would be near 52 ms instead of the measured 1.18 ms (p95).
  • GNSS: gpsd keeps owning the receiver (it also feeds chrony). Argus reads fixes from gpsd's JSON and taps the binary UBX stream through gpsd's raw watch for the raw-measurement log (gnss_raw.ubx, for PPK), interference reports (MON-RF, NAV-STATUS) and time marks. RTK corrections from an NTRIP caster are CRC-checked and written to the receiver through gpsd, so no second process ever opens the port.

Supervision and recovery

  • One camera, one thread, one pipeline. A camera fault (no frames, a pipeline error, a driver reset) is contained to that camera.
  • Supervisor every 0.5 s. A camera with no frames for stall_s (1.0 s) is restarted alone, with exponential back-off. Measured with three injected stalls: frames back 2.1–2.4 s after the last good frame, the other five untouched, re-locked at ~29 µs. A restarted camera writes a new segment run (_rNN_), so the frame-to-file mapping stays exact.
  • Safe writes. Every file has exactly one writer (no locks). Each writer flushes to the OS at least once a second, and the supervisor fsyncs every file at each checkpoint; manifest.json is replaced atomically. A write error (disk full, I/O error) stops the recording safely, and low disk stops it before it runs out. A SIGKILL in the middle of a recording leaves a usable session — this is tested.
  • One instance. An instance lock stops two Argus processes from fighting over the cameras.
  • Audit log. ~/.local/state/avrig/audit.log: one JSON line per operator or lifecycle action (record start / stop / refused, sync, offload, prune, calibration).

Health and preflight

One function evaluates the whole rig. The CLI exit codes, the GUI chips, the phone page and the recording preflight all come from it, so they can never disagree.

LevelExamplesEffect
FAILa camera missing, failed or stalled; sync required but off or lost; IMU silent (when required); disk below the minimum; a temperature over its limitBlocks recording. Recording anyway needs an explicit force, and the session is marked as forced.
WARNsync DEGRADED; a camera below its frame rate or dropping; image quality flags; no GNSS fix; clock not GNSS; no or old calibration; a camera moved on its mount; antenna fault, jamming or spoofing; RTK corrections lostShown on the chips and in the report; recording continues.

Preflight starts the cameras if needed and measures for a moment, so the rate, stalls and lock are measured, not assumed.

Files added after an offload make prune refuse that session until it is offloaded again — by design.

Offline work and the GPU

Everything heavy runs after the drive at the lowest CPU and I/O priority, refuses to start while recording, and stops itself if a recording starts. The perception models run as TensorRT FP16 engines through a small runner on the CUDA driver API with unified memory (on Orin, CPU and GPU share DRAM, so nothing is copied). One rule shaped that runner: on Jetson, CPU code must not touch managed memory while any GPU kernel of the same process is running. Running models from parallel threads violated it and crashed the process, so every TensorRT call goes through one GPU lock, held through the whole inference.
